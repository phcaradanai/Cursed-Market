# คะแนนผลงานทุกคน แยกตามระบบ — ทิศทางยืนยัน 2026-11-02

สถานะ: ผู้ใช้ยืนยันทิศทาง additive personal scoring และภาพสรุปคะแนนแล้ว; ยอดขายสองหน่วย/ความไว้ใจสะสมยืนยันแล้ว; น้ำหนัก เพดาน สูตรกันปั๊ม และการรวมกับรางวัลผู้นำเดิมยังต้องยืนยันก่อนเปลี่ยน runtime ไม่ใช่ค่าบาลานซ์ที่อนุมัติแล้ว

## สิ่งที่ยืนยันจากคำตอบล่าสุด

ทุกคนรับคะแนนจากผลงานของตนในหลายระบบ เช่น ขายของ ความไว้ใจ และกิจกรรมอื่น ไม่เลือกเฉพาะสายที่ดีที่สุด ไม่จำกัดคะแนนพิเศษไว้กับผู้ชนะสถิติคนเดียว คะแนนไม่ควรอาศัยแค่มูลค่าของและเงินเหลือ หน้าสรุปไล่แสดงทีละระบบ บอกว่าแต่ละคนทำเท่าไหร่ แล้วเติมกราฟแท่งแยกสีขึ้นไปเป็นคะแนนรวม ผู้ใช้อ้าง No Time to Relax เป็นตัวอย่างความรู้สึก ไม่ใช่ให้คัดลอก asset หรืออ้างว่าได้ตรวจเกมนั้นแล้ว

คำตอบนี้แทนข้อเสนอรับโบนัสเฉพาะสายสูงสุดที่ยังไม่ได้อนุมัติ เป้าหมายคือวางแผนได้หลายแนวทางจากการเล่นจริงและคิดผลพร้อมกันตอนจบ ไม่ล็อกคลาสใหม่

## Runtime วันนี้ — อย่าสับสนกับทิศทางใหม่

`scoring.ts` / `survival.ts`: floor((wallet + personalVault + scoredGoods) × (100 + B10−D10)/100) + ghostBonus. ของปลอม/คำสาป/ตราผู้ประเมินและ rarity มีผลตามสูตรเดิม Ghost ได้1คะแนนต่อเครดิตรายได้ที่สำเร็จแล้วครั้งเดียวหลังตัวปรับคะแนนเดิม ระบบผลงานทุกคนยังไม่ได้เชื่อม การแสดงกราฟไม่ควรคำนวณคะแนนเองจากข้อความ logs

## ตารางออกแบบหน่วยนับ — ยังไม่อนุมัติตัวเลข

| กลุ่มสรุป | ข้อมูลผลงานที่ควรเห็น | จุดยึด runtime / วิธีแยกเหตุการณ์จริง | เรื่องที่ต้องตัดสินก่อนผูกคะแนน |
|---|---|---|---|
| ทรัพย์สิน | เงินในกระเป๋า/คลัง มูลค่าสินค้าสุทธิ | `collectRun`, `collectorTotal`, `itemScoreValue` | คงคะแนนฐานเดิมหรือปรับสัดส่วนเมื่อเพิ่มผลงาน ห้ามนับของค้ำ/ของในคลังซ้ำ |
| การค้า | ซื้อสำเร็จ ขายสำเร็จ ยอดรับ ต้นทุน กำไรที่ขายจริง | NPC purchase, `trade-completed`, `market-sale`, auction settlement, price-integrity | ยืนยันแยกเป็น2รายการคะแนน: จำนวนชิ้นที่ขายสำเร็จ และยอดเครดิตที่ขายได้ทั้งหมด; ไม่ใช้กำไรสุทธิแทนสองรายการนี้ น้ำหนักและกันขายวน/สำเนา/คู่ค้าร่วมปั๊มยังต้องกำหนด |
| ความรู้ | เปิดข้อมูลใหม่ ตีราคาและผลการยอมรับ ความแม่นยำ | inspection/knowledge, accepted appraisal and item identity | ข้อมูลเดิมซ้ำไม่ควรได้เพิ่ม ต้องนิยามการตีราคาที่สำเร็จและการใช้ข้อมูลลับหลังจบ |
| สัมพันธ์ | ความไว้ใจแยก8พ่อค้า สัญญา NPC ที่สำเร็จ | positive trust mutation receipts (current `npcTrust` alone is insufficient), fulfilled NPC contract IDs | ยืนยันใช้ความไว้ใจที่ได้รับสะสมตลอดเกม แม้ภายหลังลดลง; ต้องเก็บ positive gains รายแหล่งเหตุ ไม่ใช้ค่าคงเหลือหรือค่าสูงสุดแทน และเสนอเกณฑ์กันลด/เพิ่มวน |
| การเงิน | ดอกเบี้ยที่จ่ายจริง สัญญาเงินกู้ที่ชำระสำเร็จ | `vault-interest`, funded/repaid secured-loan ledger | ฝาก/ถอน/ย้ายเงินไม่ใช่รายได้ใหม่; เงินกู้ตัวเองหรือคืนทันทีเพื่อปั๊มต้องมีเกณฑ์; แยกจาก alien-loan event |
| การเดินทาง | ช่วงที่รอด เหตุการณ์/ภารกิจที่ผ่าน การขโมย/ดวลที่สำเร็จ พลังชีวิตที่เสียจริง | unique encounter/event/duel/transaction identities; life-loss causes | การกดเลือกหรือเสียชีวิตไม่ใช่ความสำเร็จโดยอัตโนมัติ; ผู้ใช้แก้ว่าเป็นพลังชีวิตเสียสะสม ไม่ใช่จำนวนครั้งตาย ต้องกำหนดคะแนน/เพดานไม่ชวนจงใจเจ็บ |
| ชุดสะสม | จำนวนของแต่ละ rarity/ที่มา/ชนิดตอนจบ | final custody plus rarity power/provenance | เดิม×2มากสุด20/×3มากสุด40เป็นรางวัลผู้นำ ไม่ได้ยืนยันว่าให้20/40ต่อชิ้นกับทุกคน ต้องสรุปใหม่; ระวัง rarity อยู่ในมูลค่าของแล้ว |
| โลกวิญญาณ | งานสำเร็จ ค่าจ้าง ส่วนแบ่ง และคะแนนพิเศษ | `ghost-delivery` and final bonus | คงกฎที่ยืนยัน1เครดิต=1คะแนน จ่ายสำเร็จเท่านั้น; ไม่เพิ่มคะแนนซ้ำจากชนะมินิเกม/เปลี่ยนช่อง/รับงาน |

สิ่งที่เป็น input/ความเสี่ยง เช่น พลังที่จ่าย ค่าธรรมเนียม ล้มเหลว คำสาป หนี้ ไม่ต้องแปลงเป็นคะแนนบวกทุกคลิก เพียงต้องแสดงเหตุและผลครบตามระบบที่เกี่ยวข้อง การ “ครอบคลุมทุกระบบ” ไม่ใช่ให้รางวัลทุก action

## ภาพสรุปที่เสนอให้ใช้กับระบบใหม่

ใช้ ComicPhaseFrame/ComicButton/ComicTooltip และขนาด inventory เดิม ไม่มี scrolling หรือกรอบซ้อนใหม่ จัด2–4ผู้เล่นเป็นคอลัมน์กว้างเท่ากัน แท่งแนวตั้งเริ่มจากฐานเดียวกันชื่อและตัวเลขอยู่แนวเดียวกัน ลำดับคอลัมน์คงที่ขณะเล่า ไม่สลับตำแหน่งทุกครั้งที่อันดับเปลี่ยน

แต่ละขั้นไฮไลต์ชื่อระบบปัจจุบัน แสดง “ผลงาน × น้ำหนัก = คะแนนเพิ่ม” ของแต่ละคน แล้วเพิ่มส่วนสีของระบบนั้นบนแท่งรวม ใช้สีร่วมกับชื่อ/ไอคอน/tooltip จึงไม่ต้องอ่านจากสีเพียงอย่างเดียว สีกราฟเป็น semantic series ภายใน UI Comic เดิม ไม่เป็น palette ใหม่ของปุ่มหรือเมนู ไม่มีการสร้างรูปสินค้าใหม่

มีปุ่มเล่น/พัก ถัดไป และข้ามไปผลรวม ใช้การเคลื่อนไหวแบบลดลงตาม reduced-motion; เปลี่ยนหน้า เปิดเมนู หรือ reconnect ไม่ทำให้คะแนนเพิ่มซ้ำ เมื่อจบแสดงอันดับพร้อมรายละเอียดแต่ละระบบด้วยหน้า/ขั้นเดิม ห้าม dropdown ยืดลงมา

Server ต้องส่ง breakdown ที่ตัดสินแล้วเพียงชุดเดียวและผลรวมตรงกับCollector/Status/ดาวน์โหลด audit; client แค่แสดงผลและ animate ไม่มี RNG หรือคะแนนจากเวลาที่เปิดหน้า ผลดั้งเดิม/กติกาเก่าใน audit ต้อง replay ได้ตามเวอร์ชันเดิม

## ขั้นต่อไป

1. หน่วยการค้ายืนยันแยกจำนวนชิ้น/ยอดเครดิต และความไว้ใจยืนยันสะสมแล้ว; รางวัลผู้นำเดิมและเกณฑ์กันปั๊มยังต้องสรุป
2. เสนอชุดน้ำหนัก/เพดานและตัวอย่างผู้เล่น2–4คนจาก audit จริง เปรียบเทียบสัดส่วนกับคะแนนทรัพย์สิน ไม่ใส่ค่าที่ไม่ได้รับอนุมัติเป็น runtime
3. ตรวจเหตุการณ์ในระบบมี canonical facts ใดใช้ได้/ต้องเพิ่ม ห้ามนับจาก trace message ซ้ำหรือ graph dependency แล้วอ้างว่าเป็นผลงาน
4. เพิ่มเวอร์ชัน scoring/counters และทดสอบย้อน audit/โอนวน/ค้ำประกัน/สำเนา/ตาย/วิญญาณ ก่อนต่อกราฟสรุปกับ DTO กลาง

กติกาเดิมยังทำงานระหว่างออกแบบ งานสินค้าใหม่อีก48ชิ้นยังต้องทำสเปกตัวเลขแยก ไม่ใช้คำตอบเรื่องกราฟมาอนุมัติ effect เหล่านั้นโดยปริยาย

## การยืนยันเพิ่มเติม

ผู้ใช้: “แยกคะแนนระหว่างจำนวนที่ขายได้กี่จำนวนกับขายได้creditเท่าไหร่” และ “ความไว้ใจที่ได้รับสะสมตลอดเกม”. ยอดซื้อ การค้า แลกของ ภารกิจ และระบบอื่นยังต้องนิยามหน่วย/น้ำหนักให้ครบก่อน scoring runtime ใหม่. ห้ามเอาค่า trust ปัจจุบันมาทำเป็นยอดสะสมย้อนหลัง เพราะการลดลงจะทำประวัติสูญหาย.

## สัญญาข้อมูลที่ต้องออกแบบต่อ

เก็บ raw accomplishments แยกจากคะแนนที่มีสิทธิ์หลังน้ำหนัก/กันปั๊ม: salesQuantity, salesGrossCredits และ trustGainedByMerchant เป็นคนละข้อมูล ยอดขายต้องเป็นเงินที่ส่งมอบ/settleแล้ว ยกเลิกหรือ retry ไม่บวกซ้ำ ความไว้ใจนับเฉพาะจำนวนที่เพิ่มจริงหลังcap ไม่ใช่amountที่ร้องขอ และต้องไม่ทำpositive gainหายในคำสั่งที่มีทั้งการเพิ่มและลด การหักความไว้ใจภายหลังไม่ลบประวัติที่เคยได้ เกณฑ์กันปั๊มหากมีต้องอธิบายในbreakdown ไม่ปลอมrawสถิติเป็นค่าคงเหลือ. Final DTO ต้องแยก raw/eligible/weight/points ให้ตรวจที่มาของแต่ละส่วนได้.
