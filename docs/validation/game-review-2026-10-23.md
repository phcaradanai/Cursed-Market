## 1. แผนผังจุดเชื่อมหลัก

ระบบทั้งหมดผูกกันผ่านจุดร่วมไม่กี่จุด ถ้าแก้ระบบไหนให้เช็คจุดเหล่านี้ก่อน

1. **ตัวกระจาย action** `applyAppraisalAction` (`engine.ts:310-400`) แยกคำสั่งเป็น 3 ช่องทาง
   - **round** (`round-flip/raise/bank`) รับเฉพาะใน REVEAL
   - **finance** (`vault-*`, `loan-*`, `seal-*`, `crime-clear`) และ `theft-hand` รับได้ทุก phase ยกเว้น RESULTS และ**ไม่ตรวจ `done/paused`**
   - **ปกติ** ต้องยังไม่ `done` และไม่ `paused`
   - ล็อกดวล (`engine.ts:322-323`) และล็อก ability choice (`engine.ts:324`) ครอบทุกช่องทาง
2. **ลำดับเปลี่ยนช่วง** `advanceAppraisalEncounter` (`engine.ts:401-431`): bank รางวัลค้าง → settle เงินกู้ → (classic ช่วงสุดท้ายจบที่นี่) → ยกเลิกดวล → เก็บค่าชดเชย → จ่ายดอกเบี้ย → ปิดข้อเสนอตรา → รีเซ็ตที่นั่ง → หักค่าเข้า/ฟื้นพลัง → เปิดตลาด → สุ่ม event
   - ค่าชดเชยถูกเก็บ**ก่อน**จ่ายดอกเบี้ย
   - classic ช่วงสุดท้ายไม่เข้าทั้งสองขั้น
3. **`eligibleItems`** (`theft.ts:103-109`) เป็นตัวกำหนดว่าของไหน "ถืออยู่และยึดได้" ใช้ร่วมกันโดย PvP theft และ seal redemption
4. **`ownedAssetItemIds`** (`secure-storage.ts:223-225`) ใช้ร่วมกันโดย `wealth` (คะแนน classic) และ `collectRun` (คะแนน Collector) นับรวมของใน vault และของค้ำของผู้กู้
5. **`recordItemTrade` / `lastTradePrice`** มีผู้เขียนหลายเส้นทาง: ซื้อจาก NPC, P2P ที่จ่ายเงินล้วน, Dark Market, wish, bond, consign, auction, liquidation
   - ผู้อ่านคือ เงินกู้, ค่าชดเชย PvP และ liquidation
   - ของที่ไม่เคยขายด้วยเงิน (ได้จาก barter, swap หรือ event) จะไม่มีราคา จึงค้ำเงินกู้ไม่ได้และไม่เกิดค่าชดเชย
6. **bank ก้อนเดียว**: `reward` (`mechanics.ts:105-110`), ดอกเบี้ย vault, งบ Dark Market (`engine.ts:161`) และ reserved rewards ดึงจาก `state.bank` เดียวกัน
   - เงินรางวัลรอบมีบัญชีแยก (`@round-fund`) และโบนัสของถือก็มีบัญชีแยก (`@item-fund`)
7. **รอยต่อ server ↔ engine**
   - timeout เรียก `defaultAppraisalAction` (`appraisal-rooms.ts:136-149`)
   - bot เล่นใน `afterChange` (`appraisal-rooms.ts:106-135`)
   - `revealReady` กันไม่ให้รับสัญญากู้หรือข้อเสนอตราหลังคู่สัญญายืนยันไปต่อแล้ว (`appraisal-rooms.ts:67-77`)
8. **รอยต่อ engine ↔ client**
   - `appraisalViewFor` (`views.ts:45-61`) คือจุดเดียวที่ตัดข้อมูลลับ
   - client แปลข้อความ engine ภาษาไทยเป็นอังกฤษ โดยใช้ข้อความไทยเป็น key (`i18n.ts`, `en/model.ts`, `en/ui.ts`)

## 2. รีวิวรายระบบ

### 2.1 แกน engine และตัวกระจาย action

**จุดเชื่อม:** ทุก action ทำ `structuredClone(state)` → แก้ → `cancelTheftDuels` → `pauseIfNeeded` → `progress` → `expireUnavailableOffers` → `assertAppraisalInvariants`

**ข้อติ**
- **สูง [ทดสอบแล้ว] ดวลล็อกทั้งสองฝ่าย:** ระหว่างดวล ทั้งผู้ขโมยและเหยื่อส่ง `done` ไม่ได้ (ได้ error `theft-pending`)
  - parser ข้อความจาก client (ฝั่ง server) ไม่รับ `theft-timeout` จึงปลดดวลได้ทางเดียวคือ `tick()` ตอนหมดเวลา (`room-lifecycle.ts:132-139`)
  - ห้องปิดจับเวลา (`timerSettings.enabled=false`, `deadline` เป็น null): ถ้าฝ่ายใดไม่ส่งมือ ทั้ง phase ค้างตลอดไป
  - ห้องจับเวลา: เมื่อหมดเวลา `theft-timeout` จะต่อด้วย `done` ทันที (`engine.ts:389-395`) ทั้งสองฝ่ายจึงเสียเวลาที่เหลือของ phase นั้น
  - ผลคือฝ่ายใดฝ่ายหนึ่งสามารถดึงเวลาเพื่อแกล้งอีกฝ่ายได้
- **กลาง [อ่านโค้ด] ช่องทาง finance ไม่ตรวจ `done`:** ผู้ที่จบช่วงแล้วยังฝากถอน กู้ และขายตราได้ อาจเป็นความตั้งใจ แต่ยังไม่มีเอกสารยืนยัน
- **ต่ำ [อ่านโค้ด] state ของระบบใหม่อยู่นอก type:** `sinnerSeals`, `sealOffers`, `sealRedemptions`, `compensations`, `pvpBlocks` และ `crime` เข้าถึงผ่าน `as TheftState` / `as SealState` ไม่ได้ประกาศใน `AppraisalState` / `Appraiser` (`types.ts:146-285`)
  - server ต้อง cast เองเพื่ออ่าน `sealOffers` (`appraisal-rooms.ts:75`)
  - `assertAppraisalInvariants` ไม่ตรวจ `compensations`, `pvpBlocks` หรือ `crime.cases`

**ต้องแก้**
1. ให้มี timeout ของดวลแยกจาก phase (เช่น 20–30 วินาที) ที่ทำงานแม้ห้องปิดจับเวลา หรือให้ฝ่ายที่ส่งมือแล้วกด "ยอมยกเลิกดวล" ได้หลังรอครบ N วินาที
2. ย้ายฟิลด์ theft/seal/compensation เข้า `AppraisalState` และ `Appraiser` ให้มี type จริง แล้วเพิ่ม invariant ให้ครบ

### 2.2 วงจรช่วง, Survival และ Collector

**จุดเชื่อม:** `settleEncounter` (`engine.ts:175-199`) → `openRoundRewards` / `collectRun` (`survival.ts:12-31`)

**ข้อติ**
- **สูง [อ่านโค้ด] ไม่มีเพดานรอบใน survival:** `CORE2.collectorEncounter = 15` (`core2.ts:13`) และฟิลด์ `collectorAt` ใน view (`types.ts:318`) ไม่มีโค้ดใช้งาน
  - เกมจบได้ทางเดียวคือทุกคนตาย (`engine.ts:196`)
  - learning วันที่ 2026-10-16 ระบุแล้วว่าเพดานรอบเป็นทางเดียวที่รับประกันว่าเกมจบได้ แต่ยังไม่ได้ทำ
  - ตอนนี้มีเพียง bot ที่ "เกษียณ" หลังช่วงที่ 12 (`appraisal-rooms.ts:17-18`) ห้องที่มีแต่คนจริงจึงยังลากยาวได้
  - decay สูงสุด 3/ช่วง (`core2.ts:15`) และ B19 ลดความเสียหายได้
- **ต่ำ [อ่านโค้ด] แก้ phase ชั่วคราว:** `collectRun` ตั้ง `state.phase='REVEAL'` ชั่วคราวเพื่อให้ `settleLoansBeforeAdvance` ทำงาน (`survival.ts:16`) ซึ่งเปราะ และฟังก์ชันนี้ forecloses เฉพาะสัญญาที่ครบกำหนดแล้ว (ดู 2.8)

**ต้องแก้**
1. ทำ Collector deadline: ถึง `collectorEncounter` ให้เรียก `collectRun` แม้มีคนรอด และปรับ invariant (`engine.ts:481`) กับ `collectRun` (`survival.ts:13`) ที่บังคับว่าทุกคนต้องชีวิต 0
2. ส่ง `collectorAt` ไปที่ view แล้วแสดงนับถอยหลังบน HUD
3. ถ้ายังไม่ทำเพดาน ให้ระบุใน UI ว่า survival ไม่มีจำนวนช่วงตายตัว

### 2.3 เศรษฐกิจ: bank, ledger, รางวัลรอบ, Dark Market

**ข้อติ**
- **กลาง [อ่านโค้ด] bank ถูกดึงจากหลายทางในเกมยาว:** ดอกเบี้ย 4% ไม่มีเพดานจ่ายจาก bank (`secure-storage.ts:188-198`)
  - เมื่อ bank ลดลง `makeMarket` จะเปิด order น้อยลง (`engine.ts:161`) และ `reward` อื่นอาจโยน error `bank`
  - ใน survival ที่ยาวถึงช่วง 15 ขึ้นไป ผู้ฝาก 300 เครดิตได้ดอก 12/ช่วง ซึ่งมากกว่ารางวัลรอบพื้นฐาน 10
  - เป็นกติกาที่ยืนยันแล้ว ข้อนี้จึงเป็นความเสี่ยงต่อเพลย์เทสต์ ไม่ใช่บั๊ก
- **ต่ำ [อ่านโค้ด] ไม่มีตัวชี้วัดสุขภาพ bank** ใน simulation summary หรือ playtest report

**ต้องแก้**
1. เพิ่ม metric `bank` ต่ำสุดต่อ run, จำนวน order ที่ถูกตัดเพราะงบ และดอกเบี้ยรวม ลงใน `simulation/balance.ts` และ playtest report
2. ให้ bot ฝากเงินบางส่วน เพื่อวัดผลดอกเบี้ยจริง (ดู 2.12)

### 2.4 การค้า: NPC, P2P, ร้านข้ามที่นั่ง, force-buy, ค่านายหน้าและความไว้ใจ

**จุดเชื่อม:**
- `purchase` (`mechanics.ts:358-398`) จ่ายค่านายหน้า เพิ่ม trust ส่งต่อความรู้ แจก scrap/shard และบันทึกราคา
- `respond` (`engine.ts:266-297`) ใช้ `purchase` เมื่อของมาจากร้าน และย้ายของตรงเมื่อเป็น P2P

**ข้อติ**
- **กลาง [อ่านโค้ด] force-buy ข้ามความยินยอมของผู้ขาย:** `forceBuy` (`engine.ts:248-265`) ตรวจแค่ว่ามี listing และผู้ขายไม่ตาย
  - ไม่ตรวจ `listing.purchase` จึงบังคับซื้อรายการที่เปิดไว้แค่ "ให้ดู" ได้
  - ไม่ตรวจว่าผู้ขาย `done` หรือ `paused` อยู่หรือไม่
- **ต่ำ [อ่านโค้ด] ราคาจาก swap ไม่ถูกบันทึก:** P2P ที่มีการแลกของ (swap) ไม่ถูก `recordItemTrade` (`engine.ts:288`) ของที่ได้มาด้วยวิธีนี้จึงค้ำกู้ไม่ได้ ควรมีคำอธิบายใน UI
- **ต่ำ [อ่านโค้ด] ของที่ขโมยมายังขายต่อได้:** ของ `stolen` ขาย Dark Market, liquidate และ barter ไม่ได้ แต่ขายต่อแบบ P2P ได้ (`respond` ไม่ตรวจ) และ flag `stolen` ติดของไปตลอด ผู้ซื้อรายต่อไปจึงขาย Dark Market ไม่ได้เช่นกัน ซึ่งควรแจ้งผู้ซื้อก่อนซื้อ

**ต้องแก้**
1. ตัดสินใจว่า force-buy ใช้ได้กับ listing แบบ "ให้ดู" หรือไม่ แล้วเพิ่ม check ตามนั้น
2. แสดงป้าย "ของโจร" บน listing และในข้อเสนอ P2P

### 2.5 การขโมยแบบเป่ายิ้งฉุบ (พ่อค้าและผู้เล่น)

**ข้อติ**
- **กลาง [ทดสอบแล้ว] ผู้ที่จบช่วงแล้วขโมยไม่ได้:** `startTheftDuel` ต้องการ `!victim.done` (`theft.ts:132`) และ `theftViewFor` ไม่แสดงผู้ที่ done เป็นเป้า
  - ผู้เล่นจึงหนีการถูกขโมยได้ด้วยการกดจบเร็ว ซึ่งลดปฏิสัมพันธ์และกดดันให้ทุกคนรีบจบ
- **กลาง [ทดสอบแล้ว] ขโมยพ่อค้าได้เปรียบมาก:** พ่อค้าออกท่าประจำ 60% (`theft.ts:111-117`) และ UI บอกท่าประจำไว้ (`TheftPanel`)
  - เลือกมือที่ชนะท่าประจำตลอด: ชนะ 294 แพ้ 106 จาก 400 ครั้ง (≈73.5%)
  - ต้นทุนแค่ 1 พลัง โทษเมื่อแพ้คือ trust −2 และห้ามค้า 1 ช่วง ขโมยจึงอาจคุ้มกว่าซื้อ
- **กลาง [อ่านโค้ด] PvP ได้เปรียบผู้ขโมย:** ฝั่งคนจริงชนะ 50% (ไม่นับเสมอ) ได้ของทั้งชิ้น เมื่อแพ้จ่ายสูงสุด 20% ของราคาซื้อขายล่าสุดและเสียตรา 1 ใบ
  - ตราจะมีผลก็ต่อเมื่อมีคนรวมได้ 2 ใบของผู้ขโมยคนเดียวกัน และหนีได้ด้วย vault (ดู 2.6–2.7)
- **ต่ำ [อ่านโค้ด] ใช้ RNG key ซ้ำ:** ของ PvP ที่สุ่มใช้ key `${encounter}:${thief}:${victim}:theft-item` (`theft.ts:137`) เมื่อขนาดกองเท่าเดิม index จะเหมือนเดิม ไม่ได้รั่วข้อมูล แต่ควรเติม `duel.id` ใน key

**ต้องแก้**
1. ตัดสินใจเรื่อง "done แล้วปลอดภัย" ถ้าต้องการให้ขโมยได้ ให้อนุญาตเป้าที่ done แต่ยังอยู่ใน phase
2. ลดความแม่นของท่าประจำ (เช่น 45%) หรือเพิ่มโทษเมื่อแพ้ แล้ววัดผลด้วย simulation
3. วัด EV ของ PvP ใน simulation ก่อนเพลย์เทสต์

### 2.6 ตราคนบาป (sinner seals)

**ข้อติ**
- **กลาง [อ่านโค้ด] หนีการถูกยึดได้ด้วย vault:** redemption สุ่มจาก `eligibleItems` ซึ่งไม่รวม vault และของค้ำ (`seals.ts:125`) ตามกติกาที่ยืนยันแล้ว
  - ผู้ขโมยที่ฝากของดีไว้ 2 ช่องฟรี หรือซื้อช่องเพิ่ม จะเหลือแต่ของเล็กให้ยึด
  - เมื่อรวมกับข้อ 2.5 ตราจึงเป็นแรงขู่ที่อ่อน
  - เป็นความเสี่ยงต่อเพลย์เทสต์ ไม่ใช่บั๊ก
- **ต่ำ [อ่านโค้ด] ยึดของผู้ตายได้:** `redeem` ไม่ตรวจว่าผู้ขโมยยังมีชีวิต ใน survival จึงยึดของของผู้ตายได้ ซึ่งของนั้นนับคะแนน Collector ของผู้ตายอยู่ ยังไม่มีกติกายืนยันเรื่องนี้
- **ต่ำ [อ่านโค้ด] ของที่ยึดมาติด `stolen`:** ของที่ได้จากตรามีป้าย `stolen = true` (`seals.ts:153`) จึงขาย Dark Market ไม่ได้ ควรแจ้งผู้ใช้ตราก่อนเลือก

**ต้องแก้**
- ถามผู้ออกแบบเรื่องการยึดของผู้ตาย และเรื่อง `stolen` บนของที่ยึดมา
- ใส่คำเตือนใน `SinnerSeals.tsx`

### 2.7 คลังส่วนตัวและดอกเบี้ย

**ข้อติ**
- **กลาง [ทดสอบแล้ว] ย้ายเงินเข้า vault แล้วไม่ต้องจ่ายค่าชดเชย:** ผู้ขโมยที่แพ้ฝากเงินทั้งหมดเข้า vault ใน REVEAL แล้วช่วงถัดไป
  - ค่าชดเชยจ่าย 0 และถูกยกให้ (`theft.ts:254-266`)
  - ในรอบเดียวกันยังได้ดอกเบี้ย 9 เครดิตจากยอด 240
  - กติกาแต่ละข้อยืนยันแล้ว แต่เมื่อรวมกันทำให้หนีค่าชดเชยได้
  - ต้นทุนของการหนี: ถอนเงินจาก vault ได้เฉพาะ REVEAL ผู้ขโมยจึงเข้า APPRAISAL/TRADE ด้วยกระเป๋าว่าง ซื้อของด้วยเครดิตไม่ได้ และต้องทำซ้ำทั้ง 4 งวด ผู้ออกแบบควรชั่งว่าต้นทุนสภาพคล่องนี้พอเป็นโทษหรือไม่
- **ต่ำ [อ่านโค้ด] ของใน vault ไม่มีผลทั้งบวกและลบ:** การเก็บของมีคำสาปไว้ใน vault จึงไม่มีผลเสีย แต่ของนั้นยังนับคะแนน Collector (`ownedAssetItemIds`)
- **ต่ำ [อ่านโค้ด] สองระบบชื่อ vault:** `state.vault` คือคลัง Dark Market ส่วน `personalVault` คือคลังผู้เล่น ชื่อชนกันจนสับสนง่าย

**ต้องแก้ (เสนอให้ผู้ออกแบบตัดสิน)**
- ล็อกการฝากเงินระหว่างที่ยังมีงวดค่าชดเชยค้าง หรือเก็บค่าชดเชยก่อนเปิดหน้าต่างฝาก
- เปลี่ยนชื่อ `state.vault` เป็น `darkMarketVault`

### 2.8 เงินกู้มีหลักประกัน

**ข้อติ**
- **สูง [ทดสอบแล้ว] กู้ช่วงท้ายเกมแล้วไม่ต้องคืน:** `settleLoansBeforeAdvance` (`secure-storage.ts:171-183`) forecloses เฉพาะเมื่อ `encounter >= dueAt`
  - classic ช่วงสุดท้าย และ `collectRun` ตอนจบ survival ไม่ได้ปิดสัญญาที่ยังไม่ครบกำหนด
  - `ownedAssetItemIds` ยังนับของค้ำเป็นของผู้กู้
  - ทดสอบ classic 1 ช่วง: กู้ 20 จากของราคา 40 ได้ `dueAt = 4` เกมจบที่ช่วง 1 สัญญายังเป็น `active`
  - ผลคือผู้กู้ได้เงินต้นและยังได้มูลค่าของ ผู้ให้กู้เสียเงินต้นไปฟรี
  - ผู้ให้กู้ต้องกดยอมรับเองก็จริง แต่ไม่มีอะไรเตือนว่า `dueAt` อยู่หลังช่วงสุดท้าย และไม่มีการปิดสัญญาตอนจบ
  - classic: ผู้ให้กู้ยังคำนวณเองได้ว่าเกมจบช่วง 3
  - survival หนักกว่า: ไม่มีใครรู้ล่วงหน้าว่าเกมจะจบเมื่อไร สัญญาที่ทำอย่างสุจริตจึงจบแบบผู้ให้กู้เสียเงินได้เสมอ
- **ต่ำ [อ่านโค้ด] ฝั่ง UI ซ่อนลึก:** สัญญากู้อยู่ในลิ้นชัก "สมุดบันทึก" (`App.tsx:286`) จึงหาไม่ง่าย

**ต้องแก้**
1. ตอนจบเกม (classic RESULTS และ `collectRun`) ให้ settle ทุกสัญญา active
   - วิธีที่ 1: ยึดของให้ผู้ให้กู้ทันที
   - วิธีที่ 2: หักหนี้คงค้างจาก wealth ของผู้กู้แล้วคืนให้ผู้ให้กู้
2. ปฏิเสธสัญญาที่ `dueAt` เกินช่วงสุดท้ายใน classic หรือแสดงคำเตือน
3. เพิ่มเทสต์: กู้ในช่วงสุดท้ายของ classic และกู้ก่อนทุกคนตายใน survival

### 2.9 ความถูกต้องของราคา (price integrity)

**ข้อติ**
- **ต่ำ [อ่านโค้ด] ใช้ประเมินใหม่เป็นเครื่องวัดมูลค่าจริงได้:** `reappraise-owned` (`price-integrity.ts:56-73`) บอกผลว่าราคาอยู่ภายใน ±10% ของมูลค่าจริงหรือไม่ ต้นทุน 1 พลังต่อชิ้นต่อช่วง ถ้าไม่ได้ตั้งใจให้เป็นเครื่องมือตรวจ ควรให้ผลกำกวมขึ้น
- **ต่ำ [อ่านโค้ด] ยืนยันแล้วว่าไม่รั่ว:** `liquidationPrice` ส่งเฉพาะเมื่อรู้ base หรือมีราคารับรองแล้ว (`views.ts:33`)

### 2.10 การฉายข้อมูลให้ client และความเป็นส่วนตัว

**ข้อติ**
- **ต่ำ [อ่านโค้ด] view ของตัวเองเป็นแบบตัดออก ไม่ใช่เลือกใส่:** `self` สร้างจาก `structuredClone(p)` แล้วตัดออก 10 ฟิลด์ (`views.ts:47`) แม้ comment จะบอกว่า "allowlist"
  - ฟิลด์ใหม่ใน `Appraiser` จะถูกส่งให้ client โดยอัตโนมัติ เช่น `pvpBlocks`, `crime`, `theft`, `abilityChoice.itemIds` และ `buyLog` ซึ่งตอนนี้ยังเป็นข้อมูลของตัวเองทั้งหมด
- **ต่ำ [อ่านโค้ด] คะแนนความแม่นบอกใบ้มูลค่าจริงในโหมด classic:** `accuracyBonus` ส่งแบบ live (survival ซ่อนไว้ที่ `views.ts:56`)
  - ใน WS payload ค่านี้จะเพิ่ม +5 ทันทีเมื่อประเมินได้ภายใน ±10% ของ base ใครเปิด devtools ก็ใช้บอกใบ้มูลค่าจริงได้
  - UI ไม่ได้แสดงค่านี้ เสี่ยงต่ำบน LAN

**ต้องแก้**
- เปลี่ยน `self` เป็น allowlist ที่ระบุฟิลด์ทีละตัว
- ซ่อน `accuracyBonus` จนถึง REVEAL

### 2.11 Server: ห้อง, lifecycle และ timers

**ข้อติ**
- **กลาง [อ่านโค้ด] ห้องปิดจับเวลาค้างได้ถ้าคนหลุด:** ผู้เล่นที่หลุดหรือกด "ออกจากห้อง" กลางแมตช์ (`App.tsx:309-316` แค่ล้าง session) ทำให้ที่นั่งค้าง
  - host นำ seat ออกได้เฉพาะก่อนเริ่ม (`room-lifecycle.ts:107-111`)
  - ห้องปิดจับเวลาจะรอคนนั้นตลอดไป
- **ต่ำ [อ่านโค้ด] bot จบ phase เงียบ ๆ เมื่อ action ถูกปฏิเสธ:** ใน `afterChange` ถ้า action ของ bot ถูกปฏิเสธ จะ fallback เป็น `done` (`appraisal-rooms.ts:129-133`) โดยไม่มี log หรือตัวนับ
  - ใน simulation 16 runs ไม่พบการปฏิเสธ (`simulateAppraisalRun` ไม่ catch error) แต่ถ้า policy ในอนาคตส่งคำสั่งที่ใช้ไม่ได้ bot จะจบ phase ทันทีโดยไม่มีใครรู้
- **ต่ำ [อ่านโค้ด] cache ไฟล์ static:** ไฟล์ที่ไม่ใช่ HTML ได้ `Cache-Control: immutable, max-age=1y` (`app.ts:33`) รวม `public/art` และ `public/fonts` ที่ชื่อไม่มี hash เปลี่ยนภาพแล้วเครื่องที่เคยเปิดจะไม่เห็นภาพใหม่
- **ต่ำ [อ่านโค้ด] layering:** server import `appraisalBotTurn` จาก `src/simulation/` แทนที่จะเป็นโมดูลกลาง

**ต้องแก้**
1. ให้ host "ปล่อยที่นั่ง" กลางแมตช์ได้ ให้ bot หรือ default action เล่นแทนเมื่อ disconnect นานเกิน N วินาที แม้ห้องจะปิดจับเวลา
2. log หรือนับ fallback ของ bot
3. ใช้ immutable เฉพาะ `/assets/` ที่มี hash

### 2.12 Bots และ simulation

**ข้อติ**
- **สูง [ทดสอบแล้ว] simulation ไม่ครอบคลุม secure economy:** ภายใต้ `secureEconomy` ค่า `core2ActionsOf` ตัด `stealChance` / `pickpocketChance` ออก (`core2-actions.ts:133`) bot จึงไม่เริ่มขโมยเลย
  - bot ไม่มีโค้ดใช้ vault, loan, seal, crime-clear, liquidate หรือ reappraise
  - ผล 16 runs: theft=0 และ interest=0
  - ตัวเลขสมดุลทุกชุดหลัง `2dd4b0e` จึงไม่ได้วัดระบบใหม่
- **กลาง [อ่านโค้ด] bot ออกมือแบบคาดเดาได้:** เมื่อถูกขโมย bot ออก `(encounter+round)%3` (`simulation/appraisal.ts:142-143`) คนที่สังเกตจะชนะ bot ได้ทุกครั้ง
- **ต่ำ [อ่านโค้ด] bot เกษียณที่ช่วง 12:** ทั้ง sim และ server เป็นวิธีแก้ชั่วคราวแทน Collector deadline

**ต้องแก้**
1. เพิ่มพฤติกรรม bot สำหรับ theft-start (ตาม policy), ฝากเงินหรือของ, ใช้ตราเมื่อมี 2 ใบ และ crime-clear
2. bot ออกมือโดยใช้ seeded RNG ส่วนกับพ่อค้า ให้ถ่วงตามท่าประจำ
3. เพิ่ม metric ใน simulation: จำนวนการขโมยและอัตราชนะ, ค่าชดเชยที่จ่ายจริงเทียบกับที่ถูกยกให้, ดอกเบี้ยรวม และ bank ต่ำสุด

### 2.14 i18n

**ข้อติ**
- **กลาง [อ่านโค้ด] error จาก server ไม่ถูกแปล:** client แสดง `connection.error` ตรง ๆ (`App.tsx:331`) โดยไม่ผ่าน `t()` error ทุกข้อจึงเป็นภาษาไทยในโหมด English
  - ตัวอย่าง: `credit ไม่พอ` และ `ฝากถอนได้หลังรับเงินท้ายช่วงเท่านั้น` ไม่มีใน client
- **กลาง [อ่านโค้ด] note ใหม่ไม่มีคำแปล:** note ของระบบขโมยและตรา เช่น `จับขโมยได้: ได้ตราคนบาป…` (`theft.ts:194`) ไม่มีคำแปลใน client
- **ต่ำ [อ่านโค้ด] ใช้ข้อความไทยของ engine เป็น key:** การแปลใช้ข้อความไทยจาก engine เป็น key ถ้าแก้คำใน engine คำแปลอังกฤษจะหายเงียบ
  - client ยังใช้สองแบบปนกัน คือ `t()` ผ่านตาราง และ `pick(th,en)` แบบ inline

**ต้องแก้**
1. แปลจาก `error.code` ใน client (server ส่ง code มาอยู่แล้ว)
2. ให้ engine ส่ง note เป็น `{key, params}` แทนประโยคสำเร็จ
3. เพิ่มเทสต์ที่ fail เมื่อ note หรือ error ใหม่ไม่มีคำแปล EN
